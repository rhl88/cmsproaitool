# CMSPRO 应用验收技能

针对 CMSPRO 系统应用（`app/Apps/{AppName}/`）的**开发完成验收**，依据三份规范文档执行六维度全面检查，输出结构化验收报告，确保应用满足文档规定的各项技术标准和质量要求。

## 〇、规则引导（最高优先级，执行本技能前必须加载）

本技能运行于 CMSPRO 工作区，执行任何动作前必须先读取并全程遵循以下三份规则文件：

| 规则文件                            | 核心约束                                                                                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rules/01-CMSPRO开发规范.md`         | ① 全局框架保护：禁改 `vendor/`、`config/`、`routes/` 等全局代码；② 日期时间统一 `Y-m-d H:i:s`，禁止 ISO 8601；③ 排查问题先看数据，禁止从报错文案反推猜测；④ 开发环境唯一合法访问地址为 `http://<开发环境地址>`，禁止启动新服务、禁止域名+端口访问 |
| `rules/02-CMSPRO协作总则.md` | ① 全程中文思考与回复；② 收到任务先检查匹配技能；③ 验证先于完成                                                                                                                                  |
| `rules/03-通用编码准则.md`         | ① 编码前先思考：列明假设、主动澄清；② 精准修改：验收过程中发现问题只报告不擅自修复（除非用户要求）                                                                                                                 |

## 一、验收依据文档（三份，必须以最新版为准）

| 文档                         | 定位     | 验收范围                                            |
| -------------------------- | ------ | ----------------------------------------------- |
| `rules/CmsPro-v5-应用开发文档.md` | 应用怎么开发 | 目录结构、manifest、数据库、路由、API 验证、钩子、安装/卸载/升级、测试、文档交付 |
| `rules/CMSPRO-UI开发规范.md`    | 界面长什么样 | 视觉（色彩/字体/图标/间距）、组件、动效、响应式、可访问性、资源本地化            |
| `rules/应用视图规范.md`           | 页面怎么写  | 列表页/表单页结构、Layui 模板、iframe 弹窗、权限控制、公共资源          |

> 两份界面规范**必须同时阅读**、配合使用。验收时如清单条目与文档原文冲突，以文档原文为准。

## 二、触发条件

当用户出现以下意图时调用本技能：

- 应用开发完成后要求「验收」「检查」「审查质量」

- 应用发版 / 制作安装包 / 升级发布前的质量把关

- 应用升级完成后的回归验收

- 用户明确要求按六维度（功能完整性、界面一致性、交互体验、性能、兼容性、代码规范）中的任意一项或多项执行检查

> **注意**：本技能是「验收入口」，只做检查与报告，**不做修复**。验收发现的问题修复走 `app-maintenance` 技能。

## 三、验收前置约束（强制执行）

### 3.1 先读文档，再验收

验收任何应用前，必须先阅读该应用的 `doc/` 目录文档与 `manifest.json`，了解应用的功能结构、三端形态（Admin/User/Home）、依赖关系与扩展点。禁止未读文档直接开始检查。

### 3.2 验收环境约束

- 页面功能验证仅通过 `http://<开发环境地址>` 访问，禁止启动新服务、禁止域名+端口访问

- 接口测试必须走 Laravel 内置测试方案（`laravel-testing` 技能），禁止 curl + cookie + 手工 CSRF 方式

- 数据库检查优先查库取证，禁止凭猜测下结论

### 3.3 验收不产生副作用

- 验收过程禁止修改应用代码（发现问题记录到报告，由用户决定是否走维护流程修复）

- 涉及安装/卸载/升级验证时，须先向用户确认，避免破坏开发库数据

## 四、验收执行流程

```
步骤 1：确定验收范围
  → 确认应用名 / 目录（code/app/Apps/{AppName}/）、验收触发场景（开发完成 / 发版前 / 升级后）
  → 用户未指定维度时，默认执行全部六维度

步骤 2：理解应用
  → 阅读 manifest.json、doc/ 三类文档、ServiceProvider.php
  → 确认三端形态、菜单/配置声明、依赖应用

步骤 3：逐维度执行检查
  → 按第四章调度 references/ 下的维度清单
  → 每条可机检项直接运行清单内附带的命令取证；[人工] 项通过读代码 / 查库 / 页面访问判断
  → 全量测试回归：php artisan test（在 code 目录执行）

步骤 4：汇总输出验收报告
  → 按第六章模板输出报告（含总体结论、分维度明细、问题清单与整改建议）
  → 向用户汇报，询问是否对不通过项启动修复（走 app-maintenance 技能）
```

## 五、六大验收维度与清单调度

| # | 维度        | 清单文件                                     | 核心检查内容                                                                                                            |
| - | --------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 1 | 功能完整性验证   | `references/checklist-functionality.md`  | 目录结构与命名、manifest 规范、应用图标（icon 文件 / manifest 回退 / 图标接口可访问）、数据库规范、路由与 API 数据验证、钩子、安装/卸载/升级闭环、菜单与配置声明、权限体系、测试覆盖、文档交付 |
| 2 | 界面一致性检查   | `references/checklist-ui-consistency.md` | 页面完整结构、表单页布局、Layui 模板 @verbatim、公共资源引用、色彩/字体/图标、组件配置规范                                                            |
| 3 | 交互体验评估    | `references/checklist-interaction.md`    | CSRF/401 处理、错误提示、loading 与防重复点击、危险操作确认、表格无感知更新、iframe 弹窗、权限交互、动效规范                                                |
| 4 | 性能指标测试    | `references/checklist-performance.md`    | 查询优化、索引、分页、缓存同步、资源加载、动效性能、事务                                                                                      |
| 5 | 兼容性验证     | `references/checklist-compatibility.md`  | MySQL/SQLite 跨驱动、Linux 大小写敏感、响应式断点、移动端适配、可访问性、离线可用                                                                |
| 6 | 代码规范符合性检查 | `references/checklist-code-standards.md` | 全局框架保护、敏感数据加密、设置白名单、日期格式、错误码体系、Git 提交规范、.exportignore                                                             |

**执行要求**：

1. 每个维度开始前先读取对应清单文件，逐条核对，禁止跳读
2. 清单条目判定级别：**\[严重]** 一票否决 / **\[强制]** 必须整改 / **\[建议]** 优化项
3. 用户只要求部分维度时，步骤 3 仅执行指定维度，但「全量测试回归」在任何验收中都强制执行

## 六、验收判定标准

### 6.1 总体结论三级判定

| 结论        | 判定条件                                |
| --------- | ----------------------------------- |
| **验收通过**  | 六维度无 \[严重]、无 \[强制] 未整改项，全量测试全部通过    |
| **有条件通过** | 无 \[严重]，存在 \[强制] 项但已有明确整改方案且不影响核心流程 |
| **验收不通过** | 存在任一 \[严重] 项，或全量测试存在失败              |

### 6.2 \[严重] 一票否决项（源自规范原文「视为验收不通过」）

- 测试未全部通过（`php artisan test` 存在失败）

- 修改了全局框架代码（`vendor/`、`config/`、`routes/` 等保护范围）

- 界面存在 emoji 替代图标（UI 规范 8.4）

- 存在 CDN / 外部资源引用（UI 规范 8.4）

- 写接口未验证直接入库（会触发 500，开发文档第五章）

- `uninstall()` 中手动删表 / 卸载不可逆（开发文档第十二章）

- 敏感信息明文硬编码（密钥、密码、Token）

## 八、与其他技能的协作

| 环节   | 协作技能                         | 说明                                |
| ---- | ---------------------------- | --------------------------------- |
| 测试回归 | `laravel-testing`            | 全量 `php artisan test`，写接口验证用例覆盖核查 |
| 问题修复 | `app-maintenance`            | 验收不通过项的修复闭环（验收本身不修复）              |
| 架构深评 | `app-technical-analysis`     | 需要更深架构/性能分析时联动                    |
| 提交核查 | `chinese-commit-conventions` | 代码规范维度核查 Git 提交记录                 |

## 九、验收自检清单

**每次验收完成后，执行者必须自检**：

- [ ] 验收前是否已阅读应用 `doc/` 文档与 `manifest.json`

- [ ] 是否逐条核对了所选维度的清单文件，未跳项

- [ ] 可机检项是否全部运行命令取证（保留命令与输出摘要）

- [ ] `php artisan test` 全量回归是否执行且记录结果

- [ ] 报告是否按模板输出，问题清单是否标注级别、位置、规范依据、整改建议

- [ ] 验收过程是否未修改任何应用代码

- [ ] 是否向用户询问了后续处理（修复 / 提交 / 放行）
