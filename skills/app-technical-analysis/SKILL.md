# CmsPro 应用技术分析技能

## 一、技能概述

本技能用于对 `app/Apps/{AppName}/` 目录下的已开发 CmsPro v5 应用进行**全面、系统**的技术分析，并指导 CmsPro 应用开发。开发应用时，必须同步交付三类应用文档（应用信息文档、应用使用文档、应用拓展文档），确保应用文档体系完整、与代码一致。

**分析依据**：`rules/CmsPro-v5-应用开发文档.md`

**开发依据（开发应用时必须遵守，强制执行）**：

- `rules/CmsPro-v5-应用开发文档.md`：应用开发完整规范（manifest.json、命名空间、路由、视图、迁移、模型、钩子、Install、配置、注意事项等）

- `rules/应用视图规范.md`：应用视图开发规范（目录结构与命名、后台列表页/表单页结构、公共资源引用、@verbatim 等）

**分析目标**：

- 深入剖析应用的各个关键技术层面

- 结合开发文档规范要求检查合规性

- 发现技术问题、设计缺陷与优化空间

- 提供具有可操作性的改进建议

- 所有结论必须有代码示例和数据支持

## 〇、规则引导（最高优先级，执行本技能前必须加载）

本技能运行于 CMSPRO 工作区，执行任何动作前必须先读取并全程遵循以下三份规则文件：

| 规则文件                            | 核心约束                                                                                                                                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rules/01-CMSPRO开发规范.md`         | ① 全局框架保护：禁改 `vendor/`、`config/`、`routes/` 等全局代码，扩展一律走 `app/Apps/{AppName}/`；② 动手前必读开发文档与应用自身 `doc/` 文档；③ 应用调整后必须用 Laravel 内置测试验证、必须同步更新应用文档；④ 日期时间统一 `Y-m-d H:i:s`，禁止 ISO 8601；⑤ 排查问题先看数据（var\_dump/查库），禁止从报错文案反推猜测 |
| `rules/02-CMSPRO协作总则.md` | ① 全程中文思考与回复；② 收到任务先检查匹配技能；③ 设计先于编码（brainstorming）；④ 测试先于实现（TDD）；⑤ 验证先于完成                                                                                                                                            |
| `rules/03-通用编码准则.md`         | ① 编码前先思考：列明假设、主动澄清，不臆测业务；② 优先简洁：不做需求之外的抽象与配置；③ 精准修改：每行改动对应需求，不碰无关代码；④ 目标驱动：任务转化为可验证目标，循环验证至达标                                                                                                                       |

> 冲突处理：本技能流程与上述规则冲突时，以规则为准；规则未覆盖的场景按本技能流程执行。

## 二、触发条件

- 要求对某个已开发应用进行技术分析 / 架构分析

- 要求评估应用的性能瓶颈 / 性能问题

- 要求评估应用的可扩展性（水平 / 垂直扩展）

- 要求生成应用技术分析报告 / 评估报告

- 要求为已有应用新增功能、修改代码或调整视图（须同步更新应用文档）

**必填输入**：应用名称或应用目录路径（如 `CmsproDemo`、`app/Apps/CmsproDemo`）；**开发新应用时，必须先向用户确认应用标识 ID（app\_id）**（见第三章）

## 三、开发前置约束（开发应用时强制执行）

> 本技能既用于技术分析，也用于指导应用开发。**开发应用（新建应用、新增功能、修改代码、调整视图）时，必须遵守本章约束，优先级最高。**

### 3.1 开发时必须遵守的文档

开发应用前，必须深度阅读并遵守以下两份文档，**禁止凭记忆或臆测开发**：

| 文档            | 路径                                           | 适用范围                                                              |
| ------------- | -------------------------------------------- | ----------------------------------------------------------------- |
| CmsPro 应用开发文档 | `rules/CmsPro-v5-应用开发文档.md` | 应用开发完整规范（manifest.json、命名空间、路由、视图、迁移、模型、钩子、Install、配置、注意事项等）      |
| 应用视图规范        | `rules/应用视图规范.md`           | 应用视图开发规范（目录结构与命名、后台列表页完整 HTML 结构、表单页固定底部按钮栏布局、公共资源引用、@verbatim 等） |

**强制执行要求**：

1. 编写任何应用代码前，必须阅读两份文档的相关章节，按规范实现，禁止凭经验或臆测开发
2. 代码编写必须同时遵守开发文档第二十章「注意事项」全部条目
3. 视图开发必须遵守应用视图规范（如后台列表页必须包含完整 `<html>/<head>/<body>` 结构、表单弹窗必须采用「固定底部按钮栏 + 内容区自适应滚动」布局、Layui `{{# }}` 必须用 `@verbatim` 包裹、公共 CSS/JS 与 CSRF Token 必须按要求引入）
4. 开发完成后，必须对照两份文档自检，确保合规

### 3.2 开发应用必须先询问应用标识 ID（app\_id）

应用标识（app\_id）是应用的唯一标识，**决定了目录名、命名空间、表前缀、路由前缀、静态资源路径、配置键等所有映射**。开发新应用时，**第一步必须先向用户询问并确认 app\_id，禁止自行臆造、默认取值或跳过此步骤**。

**app\_id 必须符合** **`开发者唯一标识.应用标识`（`xx.xx`）格式**，**全部字符仅允许小写（点号后也必须小写，大写字母将导致安装报错「应用ID格式无效」）**：

| 部分              | 规则                   | 正则                |
| --------------- | -------------------- | ----------------- |
| developer\_slug | 小写字母开头，仅允许小写字母和数字    | `[a-z][a-z0-9]*`  |
| app\_name       | 小写字母开头，允许小写字母、数字和下划线 | `[a-z][a-z0-9_]*` |
| 连接符             | 点号（.），**最多一个点号**     | -                 |
| 总长度             | 不超过 64 字符            | -                 |

**正误示例**：

| ✅ 合法            | ❌ 违规 | 违规原因 |
| --------------- | ---- | ---- |
| `cmspro.blog`   | `niuren.Inkblog` | 含大写字母（框架校验正则仅允许小写，曾致安装报错并引发 644 处全量改名） |
| `zhangsan.shop` | `cmspro.tvbox.player` | 多个点号 |
| `cmspro.blog_tools` | `blog` | 新应用缺少开发者标识 |

**app\_id 到各层的映射规则**（以 `cmspro.demo` 为例）：

| 维度         | 映射规则                   | 示例                                    |
| ---------- | ---------------------- | ------------------------------------- |
| 目录名 / 命名空间 | 点号分段后每段 `ucfirst()` 拼接 | `CmsproDemo` / `App\Apps\CmsproDemo\` |
| 表前缀        | 点号替换为下划线               | `app_cmspro_demo_`                    |
| 路由前缀       | 点号替换为斜杠                | `/admin/cmspro/demo`                  |
| 静态资源       | 同路由前缀                  | `public/apps/cmspro/demo`             |
| 配置键        | 点号保持不变                 | `apps.cmspro.demo`                    |

**询问与验证流程**：

1. 使用 `AskUserQuestion` 工具向用户确认 app\_id（如 `cmspro.demo`），说明 app\_id 将决定目录名、命名空间、表前缀等全部映射；**提问时必须明确提示「仅允许小写字母，含大写字母（如 `niuren.Inkblog`）将无法通过安装校验」**
2. 获得确认后，必须用以下命令验证目录名，**将命令输出值作为目录名**：

   ```bash
   php -r "echo app_id_to_class_name('你的app_id') . PHP_EOL;"
   ```
3. 确保目录名、命名空间声明、ServiceProvider 引用三者完全一致（大小写敏感；Windows 不报错 ≠ Linux 正确）
4. 禁止使用多个点号（如 `cmspro.tvbox.player` 无法通过安装校验）；开发者标识不可省略

## 四、分析核心维度

必须覆盖以下 8 个核心维度，缺一不可：

### 维度 1：应用整体架构设计

**分析要点**：

- 解析 `manifest.json` 的应用声明（id、name、version、providers、hooks、install、menus、config\_groups、permissions、home\_routes 等）

- 分析 `ServiceProvider` 的路由注册、视图加载、钩子注册、配置合并策略

- 评估应用是否符合「目录隔离 / 命名空间隔离 / 数据库隔离 / 视图隔离 / 配置隔离」五大隔离原则

- 评估是否正确支持后台（admin）、用户端（user）、前端（home）三种终端

- 检查应用依赖（dependencies）声明是否合理

**架构图要求**：必须输出架构图，使用 Mermaid `flowchart` 语法绘制，包含：

- 入口层（路由 → 控制器）

- 业务层（Service / Hook）

- 数据层（Model / Migration / Database）

- 视图层（Blade / Assets）

- 外部依赖（第三方服务、外部 API）

### 维度 2：主要功能模块划分与职责定义

**分析要点**：

- 识别 Controllers / Models / Services / Hooks / Install 等核心模块

- 列出每个模块的职责清单

- 评估模块划分是否符合「单一职责原则」

- 评估模块间耦合度（Controller → Service → Model 的调用链是否清晰）

- 检查是否存在「胖控制器」（业务逻辑堆积在控制器）问题

**输出要求**：以表格形式列出每个模块的名称、文件路径、职责、对外接口。

### 维度 3：关键业务逻辑实现流程

**分析要点**：

- 追踪核心业务流程从 HTTP 入口到响应输出的完整链路

- 识别事务边界（DB::transaction）、钩子触发点（doAction / applyFilter）、外部调用（HTTP / 队列 / 缓存）

- 分析异常处理路径与降级策略

- 评估业务流程的健壮性（空值、边界值、超时、重试）

**流程图要求**：必须为每个关键业务流程输出流程图，使用 Mermaid `sequenceDiagram` 或 `flowchart` 语法。

### 维度 4：完整技术栈组成

**分析要点**：

- **前端**：Blade 模板、Layui、PearAdmin、FontAwesome、应用自有 Assets（CSS/JS）

- **后端**：PHP 版本、Laravel 版本、应用自有 composer 依赖

- **数据库**：MySQL 表结构、表前缀（`app_{app_id}_`）、索引设计

- **中间件**：`auth:admin` / `auth:web` / `web` / `throttle` 等

- **外部服务**：第三方 API、CDN、对象存储、消息队列等

- **缓存**：Redis / Memcached / 文件缓存的使用情况

**输出要求**：以表格形式列出技术栈每一层的具体技术、版本、用途。

### 维度 5：代码组织结构与模块化设计

**分析要点**：

- 检查目录结构是否符合开发文档第二章规范

- 评估命名空间隔离（`App\Apps\{AppName}\`）是否正确

- 评估视图命名空间（`{appId}::`）使用是否规范

- 评估配置键（`apps.{app_id}`）使用是否规范

- 检查是否存在跨应用调用、硬编码路径、违反隔离原则的代码

### 维度 6：潜在性能瓶颈点及具体表现

**分析要点**：

- **数据库层**：N+1 查询、缺少索引、全表扫描、大字段全量加载、未使用分页

- **内存层**：一次性加载大数据集、未释放资源、循环引用

- **外部调用**：同步 HTTP 调用未设超时、未做重试、未做降级

- **缓存层**：未使用缓存、缓存穿透 / 击穿 / 雪崩风险

- **视图层**：模板嵌套过深、未分页、未懒加载

- **并发层**：锁粒度过大、长事务、竞态条件

**数据支持要求**：必须提供量化数据，包括但不限于：

- SQL 执行次数估算（如「列表页加载 10 条数据时执行 SQL 23 次」）

- 响应时间估算（如「首屏响应约 850ms，其中 DB 查询占 420ms」）

- 内存占用估算（如「单次请求峰值内存约 45MB」）

- 代码复杂度数据（圈复杂度、函数行数、嵌套深度）

### 维度 7：系统可扩展性全面评估

**水平扩展能力**：

- 应用是否无状态（Session 是否依赖本地文件、文件上传是否依赖本地磁盘）

- 缓存是否集中（Redis vs 本地文件）

- 数据库是否可读写分离

- 是否存在单点资源（锁文件、临时目录、进程内变量）

**垂直扩展能力**：

- CPU 密集型操作识别（加密、压缩、序列化）

- 内存密集型操作识别（大数据集加载、图片处理）

- 是否存在阻塞式 I/O（同步 HTTP 调用）

**模块化扩展能力**：

- 钩子系统使用情况（是否提供自定义钩子点供其他应用扩展）

- 依赖管理（dependencies 声明是否清晰）

- 配置驱动能力（关键行为是否可配置化）

### 维度 8：技术问题、设计缺陷与优化改进空间

**分析要点**：

- 对照开发文档第二十章「注意事项」24 条规范逐项检查

- 检查安全问题（SQL 注入、XSS、CSRF、敏感信息硬编码、权限越权）

- 检查健壮性问题（异常未捕获、边界值未处理、空值未兜底）

- 检查规范违反（命名、目录结构、迁移幂等性、表/字段备注、日期格式）

- 检查可维护性问题（函数过长、圈复杂度过高、参数过多、嵌套过深）

**规范合规性检查表**：必须输出表格，列出 24 条规范逐项检查结果（合规 / 违规 / 不适用）。

## 五、分析执行流程

### 步骤 0：定位应用生命周期阶段

在动手前，先判断本次任务的场景，决定文档处理策略：

| 场景                         | 文档处理要求                                                          |
| -------------------------- | --------------------------------------------------------------- |
| **新建应用**                   | 首次交付——创建应用时即建立完整文档体系，交付三类文档（信息/使用/拓展）                           |
| **调整已有应用**（新增功能/修改代码/调整视图） | 同步更新——修改代码后，必须同步检查并更新应用 `doc/` 下对应的文档（CMSPRO 规范、开发文档 19.4 强制要求） |
| **仅技术分析**（不改代码）            | 分析现有应用，评估架构、规范合规性与改进空间                                          |

> **闭环机制**：无论何种场景，必须确保文档与应用实际状态保持高度一致。调整应用后若未同步更新文档，视为未完成任务。

### 步骤 1：定位应用目录

1. 询问用户待分析的应用名称或目录路径
2. 定位应用根目录：`app/Apps/{AppName}/`
3. 确认 `manifest.json` 存在并可读取
4. 检查应用 `doc/` 目录是否已建立，列出既有文档清单（若已有文档，先阅读理解应用结构后再操作）

### 步骤 2：收集应用元信息

1. 读取 `manifest.json` 完整内容
2. 读取 `ServiceProvider.php` 完整内容
3. 使用 Glob 列出应用目录下所有 `.php`、`.blade.php`、`.json` 文件
4. 读取 `composer.json`（如存在）和 `.exportignore`（如存在）

### 步骤 3：逐层深入分析

按以下顺序阅读并分析代码，**必须读取实际文件内容，禁止臆测**：

| 顺序 | 层次  | 文件                     | 分析重点                             |
| -- | --- | ---------------------- | -------------------------------- |
| 1  | 入口  | `ServiceProvider.php`  | 路由注册、视图加载、钩子注册、配置合并              |
| 2  | 路由  | `Routes/*.php`         | 路由定义、中间件、RESTful 合规性             |
| 3  | 控制器 | `Controllers/**/*.php` | 方法职责、参数校验、异常处理、权限控制              |
| 4  | 服务层 | `Services/*.php`（如有）   | 业务逻辑、事务管理、外部调用                   |
| 5  | 模型层 | `Models/*.php`         | 表名、$fillable、$casts、关联关系、作用域     |
| 6  | 迁移  | `Migrations/*.php`     | 表结构、索引、备注、幂等性、down() 回滚          |
| 7  | 钩子  | `Hooks.php`（如有）        | 钩子注册、app\_id 传入、自定义钩子点           |
| 8  | 安装  | `Install.php`（如有）      | 迁移兜底、卸载回滚、升级逻辑                   |
| 9  | 视图  | `Views/**/*.blade.php` | 布局独立性、@verbatim、CSRF、401 处理、资源引用 |
| 10 | 配置  | `Config/*.php`（如有）     | 配置项定义、默认值、类型                     |

### 步骤 4：规范合规性检查

对照开发文档第二十章「注意事项」24 条规范，逐项检查并记录：

- 合规：✅

- 违规：❌（附违规位置和代码片段）

- 不适用：➖（说明原因）

### 步骤 5：性能与安全评估

1. 识别所有数据库查询点，评估 N+1 风险和索引覆盖情况
2. 识别所有外部 HTTP 调用，评估超时 / 重试 / 降级策略
3. 识别所有用户输入点，评估 XSS / SQL 注入 / CSRF 防护
4. 识别所有敏感信息处理点，评估加密 / 脱敏 / 日志泄漏

### 步骤 6：生成 / 同步应用文档

按第七章规定的格式处理应用文档，并遵循以下要求：

**① 新建应用（首次交付）**：

1. 在应用 `doc/` 目录下创建三类文档：应用信息文档（特性清单）、应用使用文档（使用指南）、应用拓展文档（扩展指南）
2. 文档头部包含版本号、更新日期、应用版本、应用 ID（遵循开发文档第二十一章「应用文档规范」）
3. 文档内容必须与实际代码一致（功能、配置、接口、表结构、钩子点、扩展接口）

**② 调整已有应用（同步更新）**：

1. 修改代码后，逐项核对应用 `doc/` 下既有文档，找出与代码不一致的部分
2. 按变更内容更新对应文档章节（新增功能→补充说明；修改功能→更新描述；删除功能→移除或标记废弃；新增配置/接口→补充记录；修改表结构→更新字段说明）
3. 若应用尚无 `doc/` 目录或文档缺失，须补齐缺失的文档类型
4. **数据库变更衔接**：若本次调整涉及数据库表结构或数据变更，必须遵循 `database-change-management` 规范（提供完整可执行的 SQL 升级脚本、版本控制信息、回滚方案），并在文档中同步更新表结构、字段说明

### 步骤 7：应用开发后测试（强制）

**应用开发或调整完成后，必须进行测试验证**，优先采用 Laravel 框架内置测试方案，禁止使用 `curl.exe` + cookie 文件 + 手工抓 CSRF token 等方式进行接口测试（CMSPRO 规范明确禁止「域名 + 端口」访问，如 `http://<开发环境地址>:8000`）。

**测试依据**：`skills/laravel-testing/SKILL.md`（Laravel 测试技能，涵盖单元测试、功能测试、API 测试、数据库测试、认证测试等内置方案与最佳实践）

**测试执行流程**：

1. **定位测试目录**：应用级测试放在 `app/Apps/{AppName}/Tests/` 下，与 `Controllers`、`Services` 平级，命名空间 `App\Apps\{AppName}\Tests\...`（phpunit.xml 已配置 `app/Apps/*/Tests` 测试套件）
2. **选择测试类型**：

   - 纯逻辑（Service / Helper）→ 单元测试（`Tests/Unit`）

   - 接口 / 页面链路 → 功能测试 / API 测试（`Tests/Feature`）

   - 涉及数据库 → 使用 `RefreshDatabase` Trait（sqlite :memory: 隔离）

   - 涉及认证 → 使用 `actingAs($user, 'web')` 模拟登录

   - 涉及微信等外部依赖 → 使用 `Http::fake()` 或 Mockery 模拟
3. **编写测试用例**：覆盖正常流程、异常流程、边界值、权限拦截、校验失败等场景
4. **运行测试**：

   ```powershell
   # 在 code 目录下执行
   php artisan test --filter=类名        # 运行指定测试类
   php artisan test --testsuite=Apps     # 只跑应用级测试
   php artisan test                      # 全量回归
   ```
5. **验证通过**：确认测试全部通过（绿色）后，方可视为应用开发完成

**测试规范要点**：

- 测试数据用 `Model::create()` 构造（项目未配置 Factory 时），禁止污染真实数据库

- 断言遵循 CMSPRO 日期规范（`Y-m-d H:i:s`），禁止断言 ISO 8601 格式

- 一个测试方法只验证一个行为，命名语义清晰（如 `test_账号密码登录成功`）

- 测试失败时用 `systematic-debugging` 技能定位问题，修复后重新运行直至通过

- **必须引用真实代码片段**，禁止编造代码示例

- **必须基于实际数据估算**，禁止虚构性能数据

- 当无法获取某项数据时，明确标注「未能获取」，不得编造

### 9.2 文件读取要求

- 使用 `Read` 工具读取文件，单次读取不超过 2000 行

- 对于超过 2000 行的文件，分段读取

- 对于目录结构，先使用 `Glob` 列出所有文件，再逐个读取关键文件

### 9.3 客观性要求

- 报告必须基于事实和代码证据

- 避免使用主观评价词汇（如「糟糕」「优秀」「完美」）

- 问题描述使用中性语言（如「存在 N+1 查询风险」而非「N+1 问题严重」）

- 改进建议必须可操作、可验证

### 9.4 完整性要求

- 8 个核心维度必须全部覆盖，不得省略

- 24 条规范检查必须逐项给出结果

- 每个问题点必须附带代码示例和数据支持

- 每条改进建议必须包含改进代码、成本、收益

### 9.5 输出限制

- 报告内容控制在合理篇幅内（建议 3000-8000 行 markdown）

- 避免冗余分析，每个结论用 1-2 段话说明

- 代码示例只展示关键片段，不粘贴整个文件

## 十、与其他技能的协作

本技能在以下场景可与其他技能协作：

| 场景            | 协作技能                         | 协作方式                                                              |
| ------------- | ---------------------------- | ----------------------------------------------------------------- |
| 发现数据库设计问题需要变更 | `database-change-management` | 应用文档引用变更规范                                                        |

| 应用开发后需测试验证    | `laravel-testing`            | 应用开发或调整完成后，按 Laravel 测试技能编写并运行测试（单元/功能/API/数据库/认证测试），替代 curl 手工测试 |
