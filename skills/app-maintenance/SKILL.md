# CMSPRO 应用维护技能

针对 CMSPRO 系统已有应用的**日常开发与维护**，提供统一的执行入口，串联「分析 → 修复 → 测试 → 文档 → 发布」完整闭环，确保每次维护都规范、可追溯、可回归。

## 〇、规则引导（最高优先级，执行本技能前必须加载）

本技能运行于 CMSPRO 工作区，执行任何动作前必须先读取并全程遵循以下三份规则文件：

| 规则文件                            | 核心约束                                                                                                                                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rules/01-CMSPRO开发规范.md`         | ① 全局框架保护：禁改 `vendor/`、`config/`、`routes/` 等全局代码，扩展一律走 `app/Apps/{AppName}/`；② 动手前必读开发文档与应用自身 `doc/` 文档；③ 应用调整后必须用 Laravel 内置测试验证、必须同步更新应用文档；④ 日期时间统一 `Y-m-d H:i:s`，禁止 ISO 8601；⑤ 排查问题先看数据（var\_dump/查库），禁止从报错文案反推猜测 |
| `rules/02-CMSPRO协作总则.md` | ① 全程中文思考与回复；② 收到任务先检查匹配技能；③ 设计先于编码（brainstorming）；④ 测试先于实现（TDD）；⑤ 验证先于完成                                                                                                                                            |
| `rules/03-通用编码准则.md`         | ① 编码前先思考：列明假设、主动澄清，不臆测业务；② 优先简洁：不做需求之外的抽象与配置；③ 精准修改：每行改动对应需求，不碰无关代码；④ 目标驱动：任务转化为可验证目标，循环验证至达标                                                                                                                       |

> 冲突处理：本技能流程与上述规则冲突时，以规则为准；规则未覆盖的场景按本技能流程执行。

## 一、触发条件

当用户出现以下意图时调用本技能：

- 对已有应用进行日常维护 / 问题修复 / bug 修复

- 对已有应用新增功能、调整代码、优化性能

- 对已有应用进行升级、发布、制作升级包

- 排查线上问题、处理异常行为

- 任何涉及「修改已有应用代码」的日常开发工作

> **注意**：本技能是「维护入口」，负责编排流程；具体环节由对应技能执行（见第四章）。

## 二、维护前置约束（强制执行）

> 维护已有应用前，必须遵守以下约束，优先级最高。

### 2.1 先读文档，再动手

**维护任何已有应用前，必须先阅读该应用的** **`doc/`** **目录文档**（如 `app/Apps/{AppName}/doc/`），最大程度了解应用的功能结构、业务逻辑、扩展点和集成方式，**禁止未读文档直接动手修改**（CMSPRO 规范强制要求）。

### 2.2 遵守开发文档

- 应用代码修改必须遵守 `rules/CmsPro-v5-应用开发文档.md`

- 视图修改必须遵守 `rules/应用视图规范.md`

- 涉及数据库变更必须遵循 `database-change-management` 规范

### 2.3 禁止修改全局框架

维护时禁止修改应用外的全局框架代码（`vendor/`、`config/`、`routes/`、`app/Http/Middleware/` 等），确需修改必须先说明原因并征得确认（CMSPRO 规范）。

### 2.4 维护后必须测试

**任何代码修改后必须进行测试**，优先采用 Laravel 内置测试方案，遵循 `laravel-testing` 技能，禁止使用 curl + cookie 文件 + 域名端口方式测试。

### 2.5 维护后必须同步文档

修改代码后，必须同步检查并更新应用 `doc/` 目录下对应的文档，确保文档与代码一致（闭环机制）。

## 三、维护执行流程（完整闭环）

### 步骤 1：定位与理解

1. 确认待维护的应用名称 / 目录路径（`app/Apps/{AppName}/`）
2. 阅读应用 `doc/` 目录文档，理解架构与业务
3. 阅读 `manifest.json`、`ServiceProvider.php`，确认应用结构与版本
4. 明确本次维护的目标（修复 bug / 新增功能 / 优化 / 升级）

### 步骤 2：问题定位（如为 bug 修复）

- 若为 bug / 异常行为，使用 `systematic-debugging` 技能系统定位根因

- 若为性能问题，使用 `app-technical-analysis` 技能分析性能瓶颈

- 若为安全审计，使用 `chinese-code-review` 技能审查

### 步骤 3：实施修复 / 调整

- 按开发文档规范修改代码，遵循 `dev-standards` 通用规范

- 涉及前端代码遵循 `frontend-dev` 规范

- 涉及数据库变更遵循 `database-change-management` 规范

- 精准修改，只改动必要内容，不做无关重构

### 步骤 4：编写测试（强制）

- 按 `laravel-testing` 技能编写测试用例（可复制技能中的模板）

- 测试放在 `app/Apps/{AppName}/Tests/` 下，命名空间 `App\Apps\{AppName}\Tests\...`

- 覆盖正常流程、异常流程、边界值、权限拦截、校验失败

- 使用 `RefreshDatabase` 隔离数据库，禁止污染真实数据

### 步骤 5：运行测试验证

```powershell
# 在 code 目录下执行
php artisan test --filter=类名        # 运行本次新增/修改的测试
php artisan test --testsuite=Apps     # 运行应用级测试
php artisan test                      # 全量回归，确认不影响原有功能
```

- 确认测试全部通过（绿色）后方可继续

- 测试失败时回到步骤 2 定位，修复后重新运行

### 步骤 6：同步更新文档

- 逐项核对应用 `doc/` 目录下既有文档，更新与代码不一致的部分

- 新增功能 → 补充说明；修改功能 → 更新描述；删除功能 → 移除或标记废弃

- 涉及数据库变更 → 同步更新表结构、字段说明

- 应用 `manifest.json` 版本提升时，同步更新文档头部「应用版本」字段

### 步骤 7：代码审查

- 使用 `requesting-code-review` 技能请求审查，或自查

- 使用 `chinese-code-review` 规范审查代码质量

### 步骤 8：提交与发布

- 使用 `chinese-commit-conventions` 规范提交（`type(scope): subject` 格式）

- 分支管理遵循团队 Git 工作流（功能分支从 develop 创建，完成后合并回 develop）

- 涉及发布部署时，遵循项目 `docs/` 下交付的部署指南（如《CmsPro-v5-发布部署指南.md》，以实际交付清单为准）

- 实现完成且测试通过后，向用户提供合并 / PR / 清理等集成收尾选项，由用户决定

- **应用级独立仓库提交（强制）**：若 `app/Apps/{AppName}/` 目录内存在 `.git`（应用独立仓库），本次维护收尾时必须在该应用目录内完成提交（详见 `rules/01-CMSPRO开发规范.md` 第 3 章）：

  1. 在**应用目录内**执行 `git status` / `git diff` 确认本次变更清单
  2. `git add` 仅添加本次修改涉及的具体文件，禁止 `git add -A` / `git add .`
  3. 按 `type(scope): subject` 格式提交（scope 用应用名，如 `fix(demo): 修复项目分页参数校验`），中文描述
  4. 提交后 `git status` 确认工作区干净
  5. **禁止自动 push**：commit 完成后向用户询问是否推送到远程，由用户逐次决定

- **README.md 兜底（强制）**：若应用存在 `.git` 且根目录缺少 `README.md`，须在本次提交前基于 `manifest.json` 与 `doc/` 文档创建（结构见 `rules/01-CMSPRO开发规范.md` 第 3 章，参考 `CmsproDemo/README.md`）

## 四、与其他技能的协作

| 环节          | 协作技能                                                | 说明             |
| ----------- | --------------------------------------------------- | -------------- |
| 需求 / 设计     | `brainstorming`、`writing-plans`                     | 新增功能前先做需求分析    |
| 技术分析 / 性能评估 | `app-technical-analysis`                            | 分析架构、性能瓶颈、规范合规 |
| 问题定位        | `systematic-debugging`                              | bug / 异常行为根因定位 |
| 代码编写        | `dev-standards`、`frontend-dev`                      | 通用规范、前端规范      |
| 测试          | `laravel-testing`                                   | 编写并运行测试（强制）    |
| 数据库变更       | `database-change-management`                        | SQL 升级脚本、回滚方案  |
| 文档          | `chinese-documentation`                             | 应用文档规范         |
| 代码审查        | `chinese-code-review`、`requesting-code-review`      | 质量审查           |
| 提交 / 分支     | `chinese-commit-conventions`、`chinese-git-workflow` | 提交规范、分支管理      |
| 集成收尾        | `finishing-a-development-branch`                    | 合并 / PR / 清理   |

## 五、维护自检清单

**每次维护完成后，必须按下述清单自检**：

- [ ] 维护前是否已阅读应用 `doc/` 目录文档，理解架构与业务

- [ ] 是否遵守开发文档与视图规范，未修改全局框架代码

- [ ] 是否精准修改，只改动必要内容，无无关重构

- [ ] 是否按 `laravel-testing` 技能编写测试，覆盖正常/异常/边界/权限/校验场景

- [ ] 是否使用 `RefreshDatabase` 隔离数据库，未污染真实数据

- [ ] 是否运行 `php artisan test` 且全部通过（绿色）

- [ ] 是否同步更新应用 `doc/` 目录文档，保持文档与代码一致

- [ ] 是否遵循提交规范与分支管理规范

- [ ] 若应用目录存在 `.git`，是否已在应用目录内完成本次变更的提交（commit 后询问用户是否 push，禁止自动 push）

- [ ] 是否禁止使用 curl + cookie 文件 + 域名端口方式测试
